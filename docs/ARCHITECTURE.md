# 系统架构

## 设计原则

系统以“证据链”而不是“数据堆积”为核心。每条结论都应能回答：从哪里得到、什么时候看到、可信程度如何、是候选还是已验证。

```text
询盘 CSV/JSON ──> 统一 Lead 模型 ──> 可解释评分 ──> 分级与下一步
公开官网/邮箱 ──> Evidence 适配器 ───┘                │
自有人脉数据 ───> Relationship 路径 ──────────────────┘
                                                    │
                                      沟通浏览器插件（人工确认）
```

## 核心模型

- `Lead`：渠道询盘、企业、联系人、需求、信号、证据和合规状态的统一记录。
- `Evidence`：事实或候选线索的来源、观察时间、置信度与验证状态。
- `Qualification`：四个维度的分数、理由、缺失项、等级与建议动作。
- `RelationshipPath`：用户自有人脉中的可能引荐路径，含关系强度和同意状态。

## 隔离策略

- 核心包不直接依赖任何爬虫、搜索引擎或 CRM。
- 每个外部来源必须通过适配器转换成 Evidence。
- 外部失败不会改变已有客户档案；不确定结果标记为 `candidate` 或 `inconclusive`。
- 默认本地模式；联网提供方必须由使用者主动开启并理解数据去向。

## Harness 应用方式

桌面质量 Harness 的经验适用于“交付给客户安装并长期维护”的模块，不要求每个小脚本都完整套用。当前系统采用其关键约束：单一验证入口、可重复测试、敏感信息扫描、构建产物边界、版本与发布清单。等桌面壳或安装包形成后，再接入完整的启动/停止、数据目录和升级回滚契约。
