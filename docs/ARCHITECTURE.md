# 系统架构

## 设计原则

系统以“证据链”而不是“数据堆积”为核心。每条结论都应能回答：从哪里得到、什么时候看到、可信程度如何、是候选还是已验证。

```text
询盘 CSV/JSON ──> 渠道字段映射 ──┐
官网/邮箱/GLEIF ─> Evidence 适配器 ─┼─> 统一 Lead 模型 ─> 可解释评分 ─> 本地工作台
                                  │                                      │
自有人脉数据 ──> Relationship 路径 ┘                                      │
                                                                         └─> Lydia 分级 JSON ─> 沟通插件（人工确认）
```

## 核心模型

- `Lead`：渠道询盘、企业、联系人、需求、信号、证据和合规状态的统一记录。
- `Evidence`：事实或候选线索的来源、观察时间、置信度与验证状态。
- `Qualification`：四个维度的分数、理由、缺失项、等级与建议动作。
- `RelationshipPath`：用户自有人脉中的可能引荐路径，含关系强度和同意状态。

## 隔离策略

- 核心包不直接依赖任何爬虫、搜索引擎或 CRM。
- 每个外部来源必须通过适配器转换成 Evidence。
- 外部失败不会改变已有客户档案；不确定结果标记为 `candidate` 或 `inconclusive`。
- 默认本地模式；联网提供方必须由使用者主动开启并理解数据去向。
- 工作台不写入服务器，导入文件在浏览器页面内处理；导出文件只保留文件名，不泄露本机绝对路径。
- GLEIF 查询由本机服务转发到固定的 `https://api.gleif.org`，调用方不能指定目标网址，避免把它变成任意网络代理。
- GLEIF 请求只含企业名称和可选司法辖区；失败不会覆盖已有档案，返回结果也不会自动并入客户档案。
- 官网采集仅在使用者确认后读取一张页面，拒绝本机/内网目标、非标准端口、跨站跳转、非文本响应和超过 1 MB 的页面；所有结果均为候选证据。
- 候选邮箱在浏览器中由英文名/职能与企业域名组合；服务器只查询该域名的 MX/A/AAAA，不连接 SMTP。MX 证据类型为 `mail-domain`，不会升级具体 `business-email`。
- 候选邮箱加入询盘前必须通过企业域名一致性门禁；官网公开列出和 MX 都不能替代可投递性、联系人身份或营销同意。
- 使用者点击“加入询盘”时只填补空字段，不覆盖原有人工资料；Evidence 按 ID 去重后重新计算分级。
- 关系路径导入只在浏览器处理，拒绝状态在排序前排除，是否介绍最终由关系人决定。

## Harness 应用方式

桌面质量 Harness 的经验适用于“交付给客户安装并长期维护”的模块，不要求每个小脚本都完整套用。当前系统采用其关键约束：单一验证入口、可重复测试、敏感信息扫描、构建产物边界、版本与发布清单。等桌面壳或安装包形成后，再接入完整的启动/停止、数据目录和升级回滚契约。
