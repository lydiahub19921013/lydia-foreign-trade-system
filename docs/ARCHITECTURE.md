# 系统架构

## 设计原则

系统以“证据链”而不是“数据堆积”为核心。每条结论都应能回答：从哪里得到、什么时候看到、可信程度如何、是候选还是已验证。

```text
询盘 CSV/JSON ──> 渠道字段映射 ──┐
公开搜索 ─> 未核查 Prospect ─> 原页补证 ─┐
官网/邮箱/GLEIF ─────> Evidence 适配器 ─┼─> 统一 Lead 模型 ─> 可解释评分 ─> 本地工作台
                                         │                                      │
自有人脉数据 ──────> Relationship 路径 ┘                                      │
                                    客户空间索引 + 分区 IndexedDB <── 自动快照 ──┤
                                                                         └─> Lydia 分级 JSON ─> 沟通插件（人工确认）
```

## 核心模型

- `Lead`：渠道询盘、企业、联系人、需求、信号、证据和合规状态的统一记录。
- `Evidence`：事实或候选线索的来源、观察时间、置信度与验证状态。
- `FieldOrigin`：记录某个企业/联系人字段由哪条 Evidence 在何时填入、当前是否仍由它管理。
- `Qualification`：四个维度的分数、理由、缺失项、等级与建议动作。
- `RelationshipPath`：用户自有人脉中的可能引荐路径，含关系强度和同意状态。
- `PublicProspect`：从公开搜索或本地导入得到的候选企业、信号摘录、来源和五维候选分；与主动询盘分开。
- `Development`：冻结的首次分级基线和追加式开发事件；当前阶段、未完成待办及转化统计都从事件推导，不用事后结果覆盖初始判断。

## 隔离策略

- 核心包不直接依赖任何爬虫、搜索引擎或 CRM。
- 每个外部来源必须通过适配器转换成 Evidence。
- 外部失败不会改变已有客户档案；不确定结果标记为 `candidate` 或 `inconclusive`。
- 默认本地模式；联网提供方必须由使用者主动开启并理解数据去向。
- Exa 搜索是可选本机适配器：使用者勾选确认后，只发送当前搜索词；不发送询盘正文、关系文件或联系人资料。结果不在服务器持久化，但会作为当前工作台状态保存在使用者浏览器的 IndexedDB。
- 搜索摘要一律是 `search-candidate`，最高 49 分；没有来源链接、相关原文信号或原页核查，不得进入 shortlist/primary。
- 主动候选只有在人工确认并读取一张原始公开页面后才能转为 Lead，且来源标记为 `Public research`，不能冒充客户主动询盘。
- 工作台不把客户状态写入服务器。导入文件在浏览器页面内解析，规范化后的客户、开发活动和研究结果进入当前来源 `http://127.0.0.1:4173` 中按客户空间分区的版本化 IndexedDB 快照；导出文件只保留文件名，不泄露本机绝对路径。
- 客户空间索引只记录空间编号、名称和时间；每个空间使用独立快照键。切换前必须完成当前空间保存，保存失败时停止切换，避免把内存中的 A 客户状态写到 B 空间。
- 所有 Lydia JSON 导出包含 `lydia-workspace-reference`；重新导入时，空间编号或名称至少一项一致才允许继续。无标记的 CSV/旧 JSON 仍需人工核对当前空间。
- v0.12 的旧 `current` 快照先复制到第一个空间，再写入空间索引，最后删除旧键；迁移中断不会主动丢弃旧数据。
- IndexedDB 快照只保留明确白名单字段，不保存 Exa/官网确认勾选、密钥或未知状态；恢复后联网操作仍需重新确认。保存失败会在界面报错，不能静默视为成功。
- 本机快照未加密，只属于当前浏览器资料与来源，不会跨 `127.0.0.1`/`localhost`、浏览器或设备同步；清理浏览器站点数据也会删除它。客户空间不是账号权限或云端多租户，同时编辑同一空间也没有合并机制；JSON 导出仍是跨环境备份和迁移依据。
- GLEIF 查询由本机服务转发到固定的 `https://api.gleif.org`，调用方不能指定目标网址，避免把它变成任意网络代理。
- GLEIF 请求只含企业名称和可选司法辖区；失败不会覆盖已有档案，返回结果也不会自动并入客户档案。
- 官网采集仅在使用者确认后运行：单页模式读取指定页面；档案模式最多读取 5 张同站公开页面，并优先覆盖联系、企业介绍、工厂/能力、法定信息与产品/应用。两种模式都拒绝本机/内网目标、非标准端口、跨站跳转、非文本响应和单页超过 1 MB；不登录、不遍历整站，所有结果均为候选证据。
- 官网档案汇总字段只用于查看，底层 Evidence 始终保留各自的具体页面 URL；补充页失败会单独记录，不能把失败当作“没有该信息”。
- 官网候选默认不进入 Lead。使用者逐条勾选后，系统只从所选 Evidence 派生企业和联系字段，并记录 `review.decision=accepted` 与时间；Evidence 的 `candidate`/`verified` 状态不因此改变。
- 官网证据加入已有询盘前校验企业域名；同一主域或其子域可以匹配，不同公司域名强制阻止。询盘没有域名时允许人工补入，但仍保留来源与候选状态。
- 候选邮箱在浏览器中由英文名/职能与企业域名组合；服务器只查询该域名的 MX/A/AAAA，不连接 SMTP。MX 证据类型为 `mail-domain`，不会升级具体 `business-email`。
- 候选邮箱加入询盘前必须通过企业域名一致性门禁；官网公开列出和 MX 都不能替代可投递性、联系人身份或营销同意。
- 使用者点击“加入询盘”时只填补空字段，不覆盖原有人工资料；Evidence 按 ID 去重后重新计算分级。
- Evidence 的人工接受、驳回和修订写入最多 50 条复核历史。驳回只清空当前值仍等于原填充值的 `FieldOrigin` 字段；字段被人工改过时只停止自动管理，不覆盖人工值。
- 人工拒绝的 Evidence 即使原状态是 `verified`，也不再参与分级和已验证邮箱重复指纹；恢复后再重新计算。
- 重复检测只生成候选对。人工确认“同一客户”后只建立 `duplicateOf` 主账户关系，两个 Lead 和各自原始询盘都保留；确认“不同客户”则压下该候选。两种决定都写入追加式 `duplicateReviews`，可通过“重新判断”撤销。
- 次账户的指纹会归到主账户继续参与候选发现，避免关联后漏掉同一企业的第三条询盘；系统不会基于匹配分自动删除、覆盖或拼接客户字段。
- Lead 首次进入工作台或命令行分级时冻结当时的等级和分数。后续联系、回复、报价、样品、订单、成交、流失、待办及纠错写入 `development.events`；统计按冻结等级分组，避免用成交结果回填评分形成数据泄漏。已经人工归入主账户的次记录不重复进入转化分母。
- 开发活动撤回不会删除历史，而是追加 `activity-voided` 指向原事件；阶段、下一步和统计只使用未撤回事件。完成跟进必须引用仍开放的 `follow-up-scheduled`。
- 不联系、受限市场和已归入主账户的次记录禁止新增外联与跟进待办；入站回复仍可作为事实保存。已成交/流失客户要继续安排动作时必须先显式重新开发。
- Lydia 分级文件重新导入沟通插件时，插件只同步上次由 Lydia 管理且未被人工修改的字段。旧版或人工字段没有所有权证据时默认保留。
- 关系路径导入只在浏览器处理并保存在当前客户空间，拒绝状态在排序前排除，是否介绍最终由关系人决定。

## Harness 应用方式

桌面质量 Harness 的经验适用于“交付给客户安装并长期维护”的模块，不要求每个小脚本都完整套用。当前系统采用其关键约束：单一验证入口、可重复测试、敏感信息扫描、构建产物边界、版本与发布清单。等桌面壳或安装包形成后，再接入完整的启动/停止、数据目录和升级回滚契约。
